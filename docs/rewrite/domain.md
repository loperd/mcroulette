# Домен: сундуки, инвентарь, кошелёк

Согласовано 2026-10-19. Правила и числа — в [chest-metadata.md](./chest-metadata.md); здесь — из чего состоит домен и кто за что отвечает. Слои строятся по порядку: домен → инфраструктура → app.

## Модули

| модуль | пакет | отвечает за |
|---|---|---|
| Свод правил | `domain/rulebook` | справочник (редкости, коллекции, типы и пулы, реестр черт) и политика (параметры + правила по ситуации). Версионирован `revision`, остальные модули только читают |
| Сундуки | `domain/chest` | жизнь сундука: выдача, приземление, открытие, разрушение, мёрдж |
| Инвентарь | `domain/inventory` | предметы игрока и их состояние: получение дропа, починка, разбор, продажа, мёрдж предметов |
| Кошелёк | `domain/wallet` | общая валюта и материалы коллекций игрока |

Доступ и аккаунты (passkey, Telegram, роли) — отдельный контекст, в домен не входит. Домен не знает о JSON, БД, HTTP, времени и случайности системы: всё приходит аргументами (свод правил, ситуация, seed).

## Агрегаты

**Chest** — один сундук.

```
id, owner, type, revision, seed
contents   N слотов { item, weight }          — заморожено при выдаче
traits     [{ trait, intensity, seed }]       — меняются только приземлением и мёрджем
rarity, condition                             — выводятся и замораживаются
origin     issued(source) | merged(idA, idB)
status     available → landing(session) → opening → opened(drop) | destroyed
           available → merged
```

Инварианты: предметы набора разные и из пула своего типа; взаимоисключающих черт нет; переходы только по стрелкам; открытый, разрушенный и смёрдженный сундук ни в чём больше не участвует; дроп после фиксации не меняется.

**Inventory** — все предметы одного игрока.

```
owner, items [{ id, item, state: intact | slight | heavy | broken, origin: chest | merge }]
```

Инварианты: мёрдж — только двух одинаковых повреждённых предметов этого инвентаря; чинится только повреждённый; разобранный и проданный предмет исчезает.

**Wallet** — балансы игрока: валюта и материал каждой коллекции. Инвариант: не уходит в минус.

Сценарии, которые меняют два агрегата (починка: инвентарь + кошелёк; открытие: сундук + инвентарь), связывает app-слой в одной транзакции; домен даёт каждому агрегату его часть и доменный сервис, который считает цену.

## Объекты-значения

`Rarity`, `Tier`, `Trait`, `Wear` (по частям) и `Condition` (по худшей части), `Slot`/`Contents`, `ItemState`, `Amount` (валюта или материал), `Situation`, `Seed`, `Revision`.

## Доменные сервисы

Чистые и детерминированные: результат зависит только от свода правил, ситуации и seed.

| сервис | что делает |
|---|---|
| Issue | тип + источник + ситуация + seed → новый Chest: черты, затем содержимое (с бонусом Края), затем редкость и состояние |
| Appraise | редкость по доле предметов ≥ R |
| Assess | износ частей и состояние |
| Land | исход падения: новые повреждения, пересчёт состояния, разрушение при ударе |
| Open | разрушение перегрузкой или дроп: предмет из набора, повреждён ли он и насколько |
| MergeChests | A + B одного типа → новый C; A и B → `merged` |
| MergeItems, Repair, Salvage, Sell | экономика предметов; цены — из текущего свода |

## Приземление и разрушение решает сервер

Клиент не сообщает, что сундук ударился или сломался — он только рисует исход, который выдал сервер (контракт — [chest-breakage.md](./chest-breakage.md)).

- При начале сессии (claim) сервер считает исход падения: добавит ли удар повреждение (новая черта группы `damage` или рост интенсивности существующей), пересчитанное состояние и не разрушен ли сундук ударом (`moment: impact`).
- При открытии сервер сначала решает, не разрушит ли сундук перегрузка (`moment: opening`), и только потом роллит дроп.
- Шансы — параметры свода, зависят от износа и настраиваются правилами: `landing.damage.chance`, `landing.damage.intensity.max`, `chest.destroy.impact.perWear`, `chest.destroy.opening.perWear` (стартовые 0.3 / 0.4 / 0.1 / 0.1). Какую черту может дать удар, задаёт `landing.trait.<id>.weight` (сейчас 1 у черт повреждений, 0 у остальных).
- Разрушенный сундук получает `destroyed` без дропа. Эндпоинт `destroy`, через который это объявляет клиент, уходит.

## Доменные события

`ChestIssued`, `ChestLanded`, `ChestOpened(drop)`, `ChestDestroyed(moment)`, `ChestsMerged`, `ItemReceived`, `ItemRepaired`, `ItemSalvaged`, `ItemSold`, `ItemsMerged`, `RulebookPublished`. Из них строится статистика игрока для ситуации (число открытий, pity).

## HTTP

Все ответы — то, что решил сервер; клиент только рисует.

| запрос | тело | ответ |
|---|---|---|
| `GET /api/v1/inventory` | — | `[chest]`; при первом чтении — стартовый набор |
| `POST /api/v1/inventory/{id}/claim` | `{sessionId}` | `{chest, landing: {damage?: trait, destroyed} \| null}`; `null` — повтор той же сессии |
| `POST /api/v1/inventory/{id}/open` | `{sessionId}` | `{chest, item: ownedItem \| null}`; `null` — сундук разрушен |
| `POST /api/v1/inventory/merge` | `{a, b}` | `chest` (новый) |
| `GET /api/v1/inventory/items` | — | `{items: [ownedItem], balances: {resource: value}}` |
| `POST /api/v1/inventory/items/{id}/repair\|salvage\|sell` | — | `{resource, value}` — цена или выручка |
| `POST /api/v1/inventory/items/merge` | `{a, b}` | `ownedItem` (оставшийся) |
| `GET /api/v1/cases/{type}/catalog` | — | `[item]` — весь пул типа, `chance` — доля веса в % |

```
chest      { id, caseId, status, seed, revision, rarity, condition,
             contents: [{ item, weight }], traits: [{ id, intensity, seed }],
             origin: { source, parents? }, sessionId?, drop?: { item, state }, destroyedAt?: impact|opening, openedAt? }
item       { id, title, image, type: <редкость>, chance }   — chance содержимого — доля в % внутри сундука
ownedItem  { id, item, state: intact|slight|heavy|broken, origin: <id сундука> }
```

Ошибки: 404 — нет такого сундука или предмета у игрока (чужой — то же самое), 409 — не то состояние (другая сессия, не пара для мёржа, предмет цел, не хватает ресурсов), 400 — плохое тело.

Клиент: открытие = `claim` + `open` до падения, пока экран очищается; исход держится до показа (рулетка, разрушение), чтобы список не выдал приз раньше. Внешний вид сундука — его `traits` (id черт совпадают с модификациями модели), рулетка крутится по `contents`, фильтр и стопки инвентаря — по `rarity` сундука. Как именно разлетается разрушенный сундук, рисует клиент (`destroyedBreakage`) по моменту от сервера.

## Что ушло из старого кода

- Удар и разрушение больше не считает клиент: `demoBreakage`, `PUT …/appearance`, `POST …/destroy` удалены.
- `POST /cases/{id}/roll`, `CaseRoll` и `POST …/complete` удалены: приз выбирает `open` из содержимого сундука.
- Выигрыш — предмет в инвентаре со своим состоянием; `RewardID` у сундука остаётся как дроп.
