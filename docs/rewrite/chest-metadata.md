# Метаданные сундука: тип, экземпляр, черты, мёрдж

Целевая модель (2026-10-19), согласована с пользователем. Код пока устроен иначе — см. «Расхождения с текущим кодом». Числа помечены как заглушки баланса.

Всё решает сервер: выдаёт экземпляры, генерирует и хранит их метаданные, роллит, мёрджит. Клиент проверяет данные и рисует.

## Сущности

```
Тип сундука      наименование, модель, мир/коллекция, пул предметов типа,
                 допустимые черты и частота их выпадения при выдаче
Экземпляр        тип + метаданные:
                 ├─ содержимое   свой набор лута, выбранный из пула типа при выдаче
                 └─ черты        { id, intensity ∈ (0,1], seed, variant? }
                 + статус жизненного цикла, происхождение (из каких экземпляров собран)
Реестр черт      описание каждой черты (ниже)
```

Выводятся из метаданных (и замораживаются при выдаче — см. «Выданное заморожено»):

- **Редкость сундука** — из содержимого (+ модификаторы черт).
- **Состояние** — из черт повреждений и старения.

Редкость — свойство предметов (`common`…`legendary`), а не типа сундука. Один тип может дать экземпляры любой редкости.

## Содержимое

- Экземпляр несёт набор из N **разных** предметов пула своего типа, у каждого свой вес. **N задаётся типом**, сейчас у всех 8; мёрдж всегда внутри типа, поэтому N у обоих исходных одинаково.
- **Пул типа — 12 предметов:** 5 common, 3 uncommon, 2 rare, 1 epic, 1 legendary; веса по редкости 40 / 25 / 15 / 8 / 4. Сейчас в каждом пуле по 4 — названия дописываются в стиле коллекции.
- Редкость предметов переводится на те же пять ступеней, что и у сундуков (сейчас у предметов default / primary / legendary).
- Набор при выдаче: N предметов без повторов, выбранных из пула по весам.
- Редкость считается по количеству предметов, а не по весам: legendary с малым весом считается целым предметом. Это осознанно — игрок оценивает набор глазами. Рулетка крутится только по нему, приз выбирается при открытии.
- Набор виден игроку до открытия.

## Редкость сундука

Редкость сундука — самая высокая R, при которой доля предметов набора с редкостью ≥ R не меньше порога (**30%**, заглушка). Доля считается по количеству предметов в наборе (то, что видит игрок).

«≥ R», а не «= R»: 20% epic + 20% legendary дают epic, а не rare. Порог для common выполняется всегда, поэтому редкость определена у любого непустого набора.

Черты могут сдвигать редкость через своё влияние на содержимое (см. `loot`).

## Состояние

Состояние = f(черты групп «повреждения» и «старение»). Каждая черта задаёт свой вклад (`condition`) в те части модели, которые покрывает (корпус, крышка, замок).

- Износ части = сумма вкладов её черт, не больше 100%.
- Состояние сундука = 100% − износ **худшей** части.

```
корпус: трещины .5 + мох .2  → 70% износа
крышка: снег (не влияет)     →  0%
замок:  ржавчина .3          → 30%
состояние = 100 − 70 = 30%
```

Совпадает с UI: общий индикатор — худшая из частей (`inventory-grouping.md`).

## Реестр черт

Определяется заранее, до выдачи экземпляров, чтобы мёрдж и лут работали над стабильным набором. Сервер оперирует чертами, а не визуальными модификациями: модель решает, как черта рисуется (одна черта — одна или несколько записей её каталога модификаций, `chest-modifications.md`).

Поля черты:

| поле | смысл |
|---|---|
| `id` | стабильный идентификатор, не меняется после выдачи |
| `group` | damage / aging / weather / end |
| `tiers` | пороги интенсивности для ступеней, напр. `[.3, .6, .85]`. Лут, UI и мёрдж смотрят на ступень, визуал — на число; ребаланс меняет пороги, а не данные экземпляров |
| `variants[]` | дискретные варианты (цвет/узор), если есть |
| `rarity` | частота при выдаче |
| `condition` | вклад в снижение состояния (0 — не влияет) |
| `merge` | `reset` \| `keep { one, both }` (шанс выжить, если черта у одного / у обоих) \| `upgrade` (у обоих — шанс поднять ступень) |
| `exclusive` | группа взаимоисключения (снег ↔ иней) |
| `allowedTypes` | на каких типах черта появляется |
| `loot` | модификатор содержимого, может зависеть от ступени (напр. Край → больше редких предметов) |

Ступени у всех черт: **I ≥ .3, II ≥ .6, III ≥ .85**.

Выдача:

| группа | шанс у сундука | сколько черт | где |
|---|---|---|---|
| повреждения | 50% | 1–2 | все типы |
| старение | 20% | 1 | все типы |
| погода | 10% | 1 | все типы |
| Край | 3% | 1 | Эндер, Дракон |

Интенсивность при выдаче чаще слабая. Черта Края даёт содержимому +1 предмет редкости ≥ rare за ступень (заменяет случайный common): Край III → +3, то есть сундук минимум rare.

Группы для Эндера:

| группа | черты | condition | merge |
|---|---|---|---|
| повреждения | body-cracks, lid-cracks, shell-scuffs, latch-rust, latch-patina | да | reset |
| старение | moss, cobweb, vines, glow-lichen | да | keep |
| погода | snow, frost (exclusive) | нет | keep, одна из группы |
| Край | void-runes, end-crystals, end-blight | нет | keep, upgrade у обоих; `loot` |

## Состояние и выпавший предмет

Состояние сундука не меняет набор и вероятности ролла, а влияет на сам выпавший предмет: чем хуже состояние, тем выше шанс, что предмет упадёт **повреждённым**. Повреждённый предмет попадает в инвентарь, пользоваться им как обычным нельзя, но он остаётся в игре для дальнейшего использования (способы — открыто).

Значит, у предмета в инвентаре тоже появляется экземпляр со своим состоянием, а не только id из лут-таблицы.

- **Три степени повреждения:** слегка / сильно / сломан (плюс «целый»).
- **Шанс повреждения = износ × 0.6** (износ w = 1 − состояние): даже разрушенный сундук в 40% случаев даёт целый предмет.
- **Степень** повреждённого предмета: слегка 1 − 0.7w, сильно 0.5w, сломан 0.2w. При w = .3: 79 / 15 / 6%; при w = 1: 30 / 50 / 20%.
- **Что можно делать с повреждённым:**
  - починка — материалом коллекции предмета, одна ступень стоит базу;
  - мёрдж предметов — два одинаковых повреждённых: остаётся лучший, с шансом 70% он чинится на ступень;
  - разбор — предмет уничтожается, игрок получает материал своей коллекции (осколки Края, руда шахт…): база × множитель степени;
  - продажа/обмен — за общую валюту: база × 2.5 × множитель степени.

База по редкости предмета: common 4, uncommon 8, rare 16, epic 32, legendary 64 — ресурсы целые, так даже сломанный common даёт 1. Множитель степени: целый 1, слегка .75, сильно .5, сломан .25.

**Ресурсы:** материал у каждой коллекции свой (чинит только предметы этой коллекции) + одна общая валюта.

## Мёрдж

- Только экземпляры одного типа, только на сервере. Разрешён любой, в том числе двух целых (обычно невыгоден: из двух сундуков получается один; смысл — шанс поднять ступень общей ценной черты).
- Оба исходных экземпляра гасятся (статус `merged`), выдаётся новый с `origin: [idA, idB]`.
- **Черты:** повреждения сбрасываются; остальные выживают по `merge`. Выжившее старение продолжает снижать состояние — результат «целее», но не обязательно целый.
- **Содержимое:** наборы объединяются и случайно урезаются до N; игрок может потерять предметы любого из двух сундуков. Редкость результата пересчитывается — два uncommon могут дать rare.
- Результат детерминирован seed'ом мёрджа, который сервер хранит.

Шансы выживания черт:

| | черта у одного | у обоих | подъём ступени (у обоих) |
|---|---|---|---|
| старение, погода | 40% | 85% | 25% |
| Край | 20% | 70% | 25% |

Содержимое урезается **чисто случайно**, без перевеса редких: редкость растёт только за счёт выбора 8 из объединения.

## Конфигурация

Ни одно число и ни одно правило из этого документа не зашито в код: всё настраивает человек данными, без релиза. Значения выше — стартовая конфигурация.

### Параметры и правила

```
параметр = значение по умолчанию + правила
правило  = when (условия ситуации) → действие (set / multiply / add / allow / deny)
```

Примеры:

```
when type = ender, event = end-night          → traits.end.chance × 3
when chest.condition < .3                     → item.damage.chance = wear × .8
when collection = deep-mines                  → deny trait frost
when source = starter                         → traits.damage.chance = 0   (стартовый всегда целый)
when player.opensSinceRare ≥ 20               → pool.weight[rare+] × 2     (pity)
```

**Ситуация** (контекст, по которому проверяются условия):

| группа | поля |
|---|---|
| сундук и предмет | тип, коллекция, редкость, состояние, черты и их ступени, происхождение (выдан / мёрдж), редкость и степень повреждения предмета |
| время и события | дата/период, день недели, час, активные события (именованные, с периодом) |
| игрок | сегменты/теги, число открытий, открытий с последнего ≥ rare (pity), новичок |
| способ выдачи | starter, admin, event-reward, purchase |

Разрешение: применяются все подходящие правила; при конфликте `set` побеждает более конкретное (больше условий), при равенстве — явный `priority`. `multiply`/`add` складываются. Значения после правил ограничиваются допустимыми пределами (шанс ∈ [0, 1], N ≤ размер пула).

Уровни по умолчанию (глобально → коллекция → тип → черта) — те же правила с условием по коллекции/типу; отдельного механизма наследования нет.

### Хранение и проверка

- **Этап 1:** JSON-файлы с JSON Schema, сервер загружает и проверяет их при старте и по сигналу перезагрузки. С неверной конфигурацией (ссылки на несуществующие черты/предметы/события, сумма вероятностей ≠ 1, N > пула) сервер не применяет её и оставляет прежнюю.
- **Симулятор:** CLI на том же серверном коде прогоняет конфигурацию на заданных ситуациях (10 000 выдач, открытий, мёрджей) и печатает распределения: редкость сундуков, черты, повреждённые предметы, выход материалов и валюты. Сравнение двух конфигураций — diff распределений.
- **Этап 2:** админка поверх того же формата: редактор параметров и правил, симуляция, черновик → публикация, откат.

### Выданное заморожено

Каждая опубликованная конфигурация получает `revision`. Содержимое, черты, а также выведенные из них редкость и состояние фиксируются при выдаче вместе с revision и после перенастройки не меняются. Пересчёт — только при событии с самим сундуком (мёрдж, удар при падении), по текущим порогам. То, что считается в момент действия — шанс и степень повреждения предмета при открытии, шансы мёрджа, починка, разбор, цены, — берётся из текущей конфигурации.

## Открыто

Ничего. Все числа — стартовые значения баланса: меняются данными, а не структурой. Цена открытия сундука и источники валюты вне этого документа.

## Расхождения с текущим кодом

- `Rarity` у типа: `ChestType` (`server/internal/store/models.go`), `domain.CaseType` (`server/internal/domain/loot.go`), `CaseDefinition` и `rarityTheme` (`src/config/cases.ts`) — убрать, считать у экземпляра.
- Лут привязан к типу (`LootItem.CaseID`); у `ChestInstance` нет своего содержимого.
- Черты не хранятся на сервере: клиент выводит вид из `Seed`, `Appearance` заполняется только после удара. Серверу для мёрджа и лута нужен полный набор черт.
- Интенсивность сейчас — визуальные модификации (`appearance.modifications`), реестра черт с группами и правилами нет; группы существуют только в `chest-modifications.md`.
- Редкость предметов — default / primary / legendary (`LootItem.Rarity`), пулы по 4 предмета.
- Выигрыш хранится как `RewardID` у сундука (`ChestInstance`), отдельного экземпляра предмета с состоянием нет.
- Фильтр «по классам» в инвентаре (`InventoryScreen.tsx`) и ключ группировки (`inventory-grouping.md`) должны брать редкость и состояние экземпляра.
